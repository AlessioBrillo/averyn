# ADR-0026: Averyn–Synapse link — the contract is owned by the device, pinned by Averyn, phased in levels

- **Status:** accepted (2026-10-29, with the corrections below made before acceptance)
- **Date:** 2026-10-25
- **Deciders:** @AlessioBrillo

## Context and problem

[ADR-0010](0010-ecosystem-boundary.md) and [ADR-0014](0014-sensor-integration-contract.md) fixed the boundary: Averyn is the only system of record, Synapse is an optional sensor. They were written when the Synapse repository had no usable firmware. Since then it has a frozen, machine-readable device contract (`contracts/gatt_v1.json`, `contracts/fit_developer_fields.json`), band firmware with standard Heart Rate, Battery and Device Information services, a feature-frame characteristic, a Python SDK, a local data-plane API and a stateless worker. Three things now need deciding that those ADRs left open: who owns the contract, in which order the link is built, and what happens with the parts of the Synapse repository that assume Averyn calls it.

Differences found between [`synapse.md`](../integrations/synapse.md) v0.1 and the real contract: the stress enum has a fourth value (`3 = unknown`); the feature frame is 23 bytes (the comment in the firmware header says 26; the packed struct is 23) with per-field "not available" sentinels; RMSSD, SDNN and the RR interval are always "not available" in the current firmware (the RR field of `0x2A37` is never filled); the FIT developer fields are eight, not seven.

## Options considered

1. **Averyn owns the contract** (the table lives in Averyn, Synapse implements it). Matches v0.1, but the device is the thing that changes, and two copies of a byte layout drift.
2. **The device repository owns the contract; Averyn pins a version.** One machine-readable source, Averyn vendors a copy with its version and checksum, and golden test vectors generated by the device's own SDK prove the parser. A contract change is a version bump on one side and a pin update plus tests on the other.
3. **Averyn calls the Synapse data-plane API** (as the Synapse repository's interface document describes). Two backends again, against ADR-0010.

## Decision

**Option 2.** Averyn is the system of record; Synapse is a BLE sensor and a research SDK.

**Roles.** Averyn is the free app and the cloud; Synapse is the band and a research SDK, and the margin of the bands is what pays for the shared cloud ([ADR-0028](0028-consumer-launch-target.md)). The Synapse data-plane API stays a local research tool; Averyn never calls it. Synapse builds no consumer cloud and holds no user accounts; the provisioning-to-cloud path of its firmware is not used by the product. The Synapse worker is the only future compute point (stateless, no user identifier, per ADR-0010) and is after launch.

**Levels.**

| Level | What | Averyn code |
|---|---|---|
| L0 | The band as a standard HR strap | none |
| L1 | Feature frame v1 (consumer service) | pure parser in `shared/sensors`, native adapters, sidecar |
| L2 | `synapse_*` FIT developer fields on import | field mapping in the FIT decoder |
| L3 | Job/result plumbing to the worker | after launch, after the DPIA covers it |

The raw research service (ECG/PPG/IMU samples) is never subscribed to by Averyn (ADR-0014).

**Rules for L1.**

- A "not available" sentinel becomes `null`, never `0`.
- A frame with an unknown version is counted as a loss (`UNKNOWN_FRAME_VERSION`) and never interpreted. A gap in `sequence` is counted as a loss with its reason; a counter that jumps far back is a restart of the band, counted as a restart and followed, not as a gap.
- The timestamp of a frame is the phone's monotonic clock at reception, as for heart rate.
- Consent scopes `signal_quality` and `stress_monitoring` ([ADR-0021](0021-consent-health-data.md)). The adapter does not subscribe without a grant and re-reads it while recording. Revocation stops the stream and deletes the stored data, leaving a tombstone.
- Storage is a sidecar `<id>.synapse.jsonl`, because its lifecycle follows the consent, as for RR ([ADR-0020](0020-sensor-raw-channels.md)).
- Provenance: `source: "synapse-device"`; the `algorithm_version` is the producer's (model and firmware revision from Device Information), kept verbatim and shown as "via Synapse", never mixed into Averyn's own metrics.
- The Device Information serial is stored only as a hash, in a `devices` table (owner, vendor, model, firmware). Certificate-based provisioning is after launch.
- Wellness wording only ([ADR-0013](0013-health-data-special-category.md)).

**Pinning.** `docs/integrations/synapse.md` v0.2 names the pinned contract version. Averyn keeps a vendored copy and its sha256 in a test, and golden vectors (frame bytes → expected values). The vectors must come from the encoder of the device SDK; until the SDK has one, the ones in use are generated from the packed struct and are labelled as such. A change goes through a pull request on both sides, merged together.

**Requests to the Synapse repository** (tracked there, not done here): send the real RR in `0x2A37`; put the feature-frame layout (23 bytes, the sentinel of each field, battery, charging and sport included) in the contract JSON and check its exact size; publish the golden vectors from the SDK encoder; rewrite its Averyn interface document and mark the Synapse Cloud documents of its strategy folder as superseded (no API called by Averyn, no pages assumed, no consumer cloud); fix the `SDKCONFIG_DEFAULTS` name in its Woodpecker file. State on 2026-10-28: none of these is done.

## Consequences

- Good: one source for the byte layout; the parser is tested against the device's own encoder; Averyn works without Synapse at every level.
- Good: nothing in the launch depends on hardware that does not exist yet; L0 needs no code.
- Cost: two repositories must be changed together for a contract change; the vectors must be regenerated on a version bump.
- Cost: until the firmware fills RMSSD, SDNN and RR, L1 shows only signal quality, motion artifact and the stress class.

## Revisit when

A second sensor vendor wants a vendor-specific channel (then the rules above become a general template), or L3 starts (job credentials and the DPIA extension need their own ADR).
