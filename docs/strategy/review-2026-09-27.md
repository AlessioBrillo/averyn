# Technical review of the Synapse × Averyn strategy input

Date: 2026-09-27. Reviewed all six files in this folder against Averyn's own ADRs/CLAUDE.md and against the actual state of the `SYNAPSE-24` repo (`../SYNAPSE-24`, HEAD `076c4eb`, checked read-only the same day). This is a correction record, not a new design — the design lives in the ADRs and docs it links to.

## 0. The headline mismatch

The strategy describes a **"Synapse Band" wrist wearable** (ECG+PPG+IMU+GPS+temperature, €249, BOM €120, vendible in 6–9 months, BLE GATT + FIT + OTA + provisioning firmware "executable by one developer in 4 weeks").

The actual `SYNAPSE-24` repo is a **lab-grade research rig**: a forearm hub (ESP32-S3 + AD8232 ECG + MAX30102 PPG + ICM-20948 IMU, no GPS) plus separate head-pod/in-ear EEG satellites, explicitly framed in its own `Architecture.md` as "experimental phase, no regulatory/commercial constraints". There is no PCB, no enclosure, no FIT writer, no OTA, no provisioning, no MQTT, and the BLE service streams **raw** 64-byte samples over the **Nordic UART Service UUID** (not a Synapse-specific one) at ~664 notifications/second, with the compressed features (HR, RMSSD, SDNN, SQI, motion) computed but only logged, never sent. The firmware likely does not compile as committed (a `static` task function called from another file; a source file missing from CMake; the battery ADC channel colliding with the ECG channel). CI's firmware "unit test" step builds but runs nothing.

None of this means the idea is bad — it means: **Averyn cannot depend on any of the strategy's device-side specifics today.** Everything below is written so Averyn only commits to a *contract* a future, corrected Synapse firmware must meet, never to the current strategy's code samples.

## 1. Protocol/technical errors (file 02, 03, 04)

| # | Claim | Problem | Correction |
|---|---|---|---|
| 1 | Service UUID `53594E41-5053-452D-4241-4E44-000000000000` | 6 hyphen-groups; a UUID is `8-4-4-4-12` hex digits. `UUID.fromString` throws. | Generate one random 128-bit UUID (`uuidgen`), don't hand-encode ASCII into it. |
| 2 | `CHAR_ECG_RAW` etc. use standard characteristic `0x2A38` for "HRV/RR" | `0x2A38` is *Body Sensor Location*. RR intervals are a variable-length field **inside** the standard `0x2A37` Heart Rate Measurement, gated by a flag bit. | Use `0x2A37` for HR+RR; don't invent a meaning for `0x2A38`. |
| 3 | ECG raw stream: `int16[500]` per 1 s notify (file 04) | 1000 bytes; ATT notification payload is capped at 512 bytes total, and typical negotiated MTU on phones is 185–247 bytes, i.e. real payload ~180–240 bytes per notify. | Raw ECG never goes over BLE to a phone at all (see §5). If a feature stream is chunked, each chunk must fit MTU−3 bytes with an explicit sequence number for reassembly. |
| 4 | Sleep stage enum: 4 classes in file 02 (`0=wake,1=light,2=deep,3=REM`), 5 classes in files 03/04 (`W/N1/N2/N3/REM`) | Same field, two incompatible encodings across documents written the same day. | One canonical enum, see [`docs/integrations/synapse.md`](../integrations/synapse.md). |
| 5 | FIT developer fields as "struct" types (`synapse_signal_quality`, `synapse_hrv_detail`, file 02) | The FIT SDK's developer-data mechanism has no struct/composite field type; every developer field is a single scalar (uint8/uint16/…). File 04 already gets this right (one row per scalar). | Use file 04's flat table as the only canonical one; delete the struct version. |
| 6 | "Sleep staging (YASA)" runs on Band data | YASA is an EEG-based classifier; SYNAPSE-24's own `signal_quality/eeg.py` confirms it's fit to Sleep-EDF EEG channels. Band v1 (per the strategy) and the real forearm rig both lack EEG. | Either ship EEG (headband, a different milestone) or use a PPG/IMU-only sleep-probability heuristic and *call it that* — a heuristic with lower accuracy, not "YASA sleep staging". Never advertise a technique the input data can't support. |
| 7 | "TimescaleDB Community is Apache-2.0, compatible with AGPL" (file 03, Consequences) | Compression, retention policies, continuous aggregates and other "Community" features are gated by the **Timescale License (TSL)**, a source-available but non-OSI license, not Apache-2.0. Only the base extension is Apache-2.0. | If a time-series store is ever needed (it isn't, under ADR-0010 — see §6), plain PostgreSQL partitioning or an Apache-licensed alternative, not an unreviewed TSL dependency. |
| 8 | `sessions`/`metrics`/`devices` as TimescaleDB hypertables (file 03) | `create_hypertable` requires the partitioning column in every unique/primary key; the given `PRIMARY KEY (id)` on tables partitioned by `created_at`/`started_at`/`computed_at` fails outright. `devices` (one row per device, rarely inserted) isn't time-series data and shouldn't be a hypertable at all. | N/A under ADR-0010 (no separate time-series store). |
| 9 | MinIO as the S3-compatible store (file 03) | Averyn's own [ADR-0006](../adr/0006-postgres-postgis-s3-storage.md) already rejected MinIO for self-hosting: its Community Edition/container images were discontinued. File 03 pins `minio/minio:RELEASE.2024-08-17` anyway. | SeaweedFS, per ADR-0006 — one object-storage decision for the whole ecosystem, not two. |
| 10 | "Authentik Realm Configuration" (file 03) | The actual JSON (`serviceAccountsEnabled`, `directAccessGrantsEnabled`, `realm_access` claim shape, `keycloak/realm-export.json` path) is a **Keycloak** realm export. Authentik has no concept of a "realm" in that form. The container image `ghcr.io/goauthentik.io/server` is also missing a required `:tag`. | Pick one IdP and write config that matches it — see [ADR-0011](../adr/0011-identity-oidc.md). |
| 11 | Compose stack (file 03) | Several breaking issues: `inference-worker` has a mandatory `deploy.resources.reservations.devices` GPU block — the stack fails to start without an NVIDIA GPU, contradicting the doc's own "CPU-only default" claim. EMQX ports 1883 (plaintext MQTT) and 18083 (admin dashboard) and the MinIO console (9001) are published directly to the host with a hardcoded `minioadmin` credential. `oauth2-proxy`'s `upstreams` lists `rest-api:8001` while the `rest-api` service's own Dockerfile/environment implies it listens on 8000. The Caddyfile's `import {$SYNAPSE_DOMAIN}` line is not valid Caddyfile syntax (`import` takes a snippet name or file path, not a live env-var-expanded site block). | N/A under ADR-0010; if any of this is rebuilt for the standalone worker, treat it as new infra, not a copy-paste of file 03. |
| 12 | Device provisioning: cloud generates and sends `device_key` over BLE (file 02, `SynapseDeviceManager.provisionNewBand`) | Contradicts file 04's own security section ("private key never leaves the device") and basic mTLS practice — a private key transiting cloud→phone→BLE is not private. | CSR flow only: device generates its keypair, sends a CSR, cloud/CA returns a signed cert. File 04's flow is the one to keep. |

## 2. Conflicts with Averyn's own architecture and rules

| # | Issue | Rule violated | Correction |
|---|---|---|---|
| 13 | Sample code uses `Context`, `BluetoothGatt`, platform BLE callbacks and `java.io.File` directly inside a file path under `commonMain` (`shared/tracking/.../SynapseBleAdapter.kt`), plus package `averyn.*` | [ADR-0004](../adr/0004-kotlin-multiplatform-shared-native-ui.md): `shared/` is pure Kotlin, no platform deps. CLAUDE.md: real package root is `dev.averyn.*`. | BLE/GATT stays in the native app layer; `shared/` only gets a pure frame parser (bytes in, `SensorSample` out). See [ADR-0014](../adr/0014-sensor-integration-contract.md). |
| 14 | Cloud-computed `ReadinessMetric`/`SleepQualityMetric`/`StressTrendMetric` proposed as new types in `shared/metrics` with a `@MetricDefinition` annotation (file 02) | `@MetricDefinition` doesn't exist in the codebase. More importantly: Averyn's metrics rule (CLAUDE.md, [docs/metrics/template.md](../metrics/template.md)) is "one Kotlin implementation, versioned, reproducible from raw samples" — these values are computed by a third-party Python/ONNX pipeline Averyn doesn't control or can't reproduce deterministically offline. | Model them as **imported** data (`source: "synapse-worker"`, an *external* `algorithm_version` string Averyn stores but doesn't own), not as Averyn metrics. See ADR-0014. |
| 15 | `SynapseCloudClient.getReadiness(userId, date)` etc. authenticate with one static **service-account** token and pass `user_id` as a query param (file 02) | Classic confused-deputy / IDOR: any caller holding that one service token can read any user's health data by changing the parameter. Averyn's own [`data-classification.md`](../privacy/data-classification.md) requires per-object access checks on Restricted data. | Per-user delegated tokens (OIDC token exchange or a job-scoped credential minted per request), never one shared secret standing in for every user. See ADR-0011. |
| 16 | Two full backends, two auth systems, two object stores, two user/device/session tables (Averyn's Ktor+Postgres+SeaweedFS vs. Synapse Cloud's FastAPI+Timescale+MinIO+Authentik) | Contradicts vision principle 9 ("extensible without prematurely becoming microservices") and principle 10 ("sustainable for a single developer"), and the "self-host in 30 minutes" promise (file 00) — the combined stack is 16+ containers. | ADR-0010: one backend (Averyn/Ktor), one auth boundary (ADR-0011), Synapse reduced to a stateless inference worker with no user data of its own. |
| 17 | Two independent GPS sources (phone location + Band's GPS module) and two upload paths (Band→Wi-Fi/MQTT→cloud direct, and Band→BLE→phone→Averyn→cloud) with no reconciliation rule | Silent duplicate/conflicting activities; violates "no silent data loss" (CLAUDE.md) in the opposite direction — silent double-counting. | One canonical path and source per activity, explicit merge/dedup rule — see ADR-0014 §"Canonical GPS source". |
| 18 | File 03 is titled "ADR-0010" | Averyn already numbers its own ADRs sequentially in `docs/adr/`; the next free number in *this* repo is 0010. A document outside this repo claiming that number will collide the day it's ported in. | This review reserves 0010–0014 in Averyn's sequence for the corrected decisions; file 03 keeps its own numbering in whatever repo it belongs to. |
| 19 | Sequencing: file 00's "Phase 2 (months 3–5)" bundles `SynapseBleAdapter`, `SynapseCloudClient` and the Web Synapse section, but MVP-1 (accounts, sync, backend) — a prerequisite for all three — is file 00's own "Phase 3 (months 5–9)" | Self-contradictory roadmap: integration work is scheduled before its dependencies. | [`docs/product/roadmap.md`](../product/roadmap.md) places any Synapse-consuming work after MVP-1, with generic BLE HR support (no Synapse dependency) as the first, MVP-2 step. |

## 3. Business, legal and timeline concerns

| # | Issue | Correction / where tracked |
|---|---|---|
| 20 | HRV/ECG/stress/sleep data is "special category" personal data under GDPR Art. 9, not ordinary personal data — needs explicit consent per purpose, a documented legal basis, and a DPIA before any hosted processing. | [ADR-0013](../adr/0013-health-data-special-category.md), [`data-classification.md`](../privacy/data-classification.md). |
| 21 | "Readiness"/"stress"/HR from an uncertified ECG lead risk crossing into medical-device claims (EU MDR 2017/745) if marketed as diagnostic; a radio device sold in the EU needs RED (radio equipment directive) conformity, not just generic "CE/FCC/RoHS". | Kept as a flagged constraint in `business-model.md`; needs actual legal review before any sale, not solved by an AI assistant. |
| 22 | €249 including VAT is ~€204 net revenue in Italy (22% VAT); against a €120 BOM that's ~€84 gross margin before packaging, shipping, payment fees, returns, warranty and one-off costs (certification, tooling) that run in the tens of thousands of euros. "€129 margin funds 3–4 years of cloud" overstates the real number roughly 1.5×, and doesn't say who funds the cloud cost of users who never buy hardware. | [`docs/product/business-model.md`](../product/business-model.md) redoes the math and states assumptions explicitly; GPS-only users' costs are covered by fair-use quotas + donations/club plans per your decision, not by hardware margin. |
| 23 | AGPL-3.0 code distributed through Apple's App Store needs the distributor to hold full copyright (or an added store-distribution exception) — this is the same decision as the CLA, not a separate one. | [ADR-0012](../adr/0012-cla-and-store-distribution.md), closes the pending item in [ADR-0002](../adr/0002-license-agplv3.md). |
| 24 | Timelines in the input ("firmware BLE+FIT+OTA+provisioning in 4 weeks, solo", "Band vendible in 6–9 months") are not consistent with the actual state of `SYNAPSE-24` (§0) or with one developer plus 1–2 people arriving soon. | Not something to fix in a doc — flagged here so it isn't quietly treated as a commitment. Roadmap only tracks Synapse work Averyn is *ready to consume*, not the firmware's own schedule (that belongs to `SYNAPSE-24`'s own roadmap). |

## 4. What to do with `SYNAPSE-24`

Not this repo's job to fix, but worth relaying to that repo's own backlog since this review already found it: the BLE service should move off the Nordic UART UUIDs onto a real Synapse UUID, expose standard Heart Rate/Battery/Device Information services, send the already-computed compressed features instead of (or alongside) raw samples chunked to fit MTU, and get its firmware CI to actually execute the "unit test" step rather than just compile it.
