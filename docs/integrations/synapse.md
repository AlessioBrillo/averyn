# Synapse integration contract

Status: v0.4 — draft (2026-11-07; the sections on the pin and what is in place are rewritten with the code of the pairs of pull requests that follow ADR-0030). What Averyn requires from, and does with, a Synapse device, under [ADR-0010](../adr/0010-ecosystem-boundary.md), [ADR-0011](../adr/0011-identity-oidc.md), [ADR-0014](../adr/0014-sensor-integration-contract.md) and [ADR-0026](../adr/0026-averyn-synapse-link.md). It supersedes the device-side specifics in [`docs/strategy/`](../strategy/README.md) (corrections in [`review-2026-09-27.md`](../strategy/review-2026-09-27.md)). v0.2 replaced the byte-level tables of v0.1: the device repository owns them. v0.3 adds the roles of the two products, the way a contract change travels and the pairing experience.

Level L0 needs no code. Level L1 is scheduled in the [roadmap](../product/roadmap.md#synapse-track) as a beta and is the first item on the cut line; its pure core is in place (section 1b), the native adapters, the sidecar and the server side wait for a prototype that produces real frames and for the approval of [ADR-0026](../adr/0026-averyn-synapse-link.md).

## Roles of the two products

| | Averyn | Synapse |
|---|---|---|
| What it is | The free app (iOS, Android, web) and the cloud | A band that talks BLE, plus a research SDK |
| Owns | Accounts, consent, activities, the only system of record | The device, its firmware, the byte-level contract |
| Pays for | The managed cloud, from donations and from the margin of the bands sold ([business model](../product/business-model.md)) | The band, sold at a price that includes that margin |
| Never does | Call the Synapse data-plane API. It subscribes to the raw research streams only with the `raw_signals` consent ([ADR-0030](../adr/0030-synapse-contract-v2-1-and-raw-signals.md)) | Run a consumer cloud or hold user accounts; the provisioning path to a cloud in the firmware is not used by the product |

Data path: band → BLE → phone (Averyn) → sync → Averyn cloud. Nothing else. The pages and calls that the Synapse repository's own interface document once assumed (an HTTP pull by Averyn, `/synapse/*` pages) are dropped: that document is rewritten in the device repository ([#72](https://github.com/AlessioBrillo/averyn/issues/72)).

## Principle

A Synapse band is one BLE sensor among others. Averyn's generic sensor support (standard Heart Rate, Battery, Device Information, FIT import, HealthKit, Health Connect) works with **zero** Synapse-specific code. Everything below the first level is the additional, optional layer for the band's extra signals, and it never gates a core feature.

## 1. The pinned contract

The contract is owned by the device repository (`SYNAPSE-24`): `contracts/gatt_v2.json` (the consumer GATT characteristics, the feature frame, the status record, the stream table and the control point), `contracts/raw_frame_v1.json` (the raw research frame) and, for the research service UUIDs that only live there, the retired and byte-identical `contracts/gatt_v1.json`. Averyn pins one version of each, and keeps the device repository's synthetic sessions as fixtures:

| What | Pinned |
|---|---|
| Contract version | Consumer GATT **2.2**, raw frame 1.0 (GATT v1 is retired: no v1 band ever existed and Averyn has no v1 parser) |
| Source | `SYNAPSE-24` `master` at `e1f1dc9` |
| Vendored copies and sha256 | `shared/sensors/src/jvmTest/resources/synapse/`: `gatt_v2.json` `dfda3fa5…c342`, `raw_frame_v1.json` `1f1db14d…3553`, `gatt_v1.json` `0c6b9e38…88a9`, the vectors and the sessions below. `SynapseContractPinTest` checks every hash and compares the constants of the code (UUIDs, sizes, offsets, flags, units, control opcodes) with the vendored JSON, so a changed contract fails the build until it is re-pinned on purpose |
| Golden vectors and sessions | `consumer_v2_vectors.json` (6 feature frames, 2 status records) and `raw_frame_vectors_v1.json` (6 valid frames, 7 refused), both generated by the device SDK's encoder, not by hand; `band_scenarios_v1.json` (seven raw sessions and one L1 session, each with an answer key computed by a reference implementation of the contract's rules); `session_60s.*` (the files a phone writes, see below). `SynapseVectorsTest` and `SynapseFixturesTest` replay all of them |

**How a contract change travels.** (1) A pull request in the device repository changes `contracts/` and bumps the version, regenerates the vectors and the sessions with the SDK encoder and updates its own checks; (2) a pull request here updates the vendored copies, the hashes in `SynapseContractPinTest` and the parsers, with the vectors and sessions as tests; (3) neither merges alone — the second is opened against the first and both are merged the same day. A frame whose version a parser does not know is counted as a loss and skipped, never interpreted (ADR-0014). The device repository's `.gitattributes` makes the contract files LF on every platform, so that the hash of a checkout is the hash of the index.

**The pin in force (ADR-0030, accepted 2026-11-07).** Averyn pinned contract 2.2 once, with the parsers, and dropped v1. Since 2.2 a stream's sequence advances only when the band's stack accepted the frame: a refused notification is retried with the same number, so a hole is a frame lost after the stack took it, and samples the band had to discard travel in `dropped`.

### 1b. What is in place

`shared/sensors` (pure Kotlin, no platform types, never throws on a short or foreign frame) reads: the feature frame (`parseSynapseFeatureFrame`, 27 bytes: fractions are `raw / 254`, the RR is `1/1024 s`, `charging` only when the band has a power monitor, a stress class of `unknown` is kept apart from a model that did not run); the status record (`parseSynapseStatus`, 40 bytes); the raw frame (`decodeSynapseRawFrame`: a 12-byte header and values in s8/s16/s32, refused in the order of the contract's reference codec); the stream table with display units taken from the contract (`SYNAPSE_STREAMS`: a gyroscope travels in mrad/s and is shown in °/s); the control point (`SynapseControl`: start, stop, feature rate, `set_time`); the sidecar record format (`u16 length | i64 received_ns | frame`); and `SynapseRawSession`, which keeps the contract's account of a recording: per stream the frames and values, what the link lost, what the band says it dropped, repeats and late frames, restarts, and the band's clock extended past its 32-bit wrap. Every field marked "not available" is **null**, never zero; a value out of range is null too. `SynapseSequenceTracker` counts the frames the link lost from the 16-bit counter (it wraps; a repeat or an old frame is counted apart and does not move the counter back; a counter that restarts, because the band rebooted, is counted as a restart and followed). The standard `0x2A37` parser follows the Bluetooth contact bits (2 = not detected, 3 = detected, 0 and 1 = no information) and keeps the heart rate of a notification whose RR list ends in a stray byte.

What Averyn relies on, without copying the tables:

- **Standard services** `0x180D` (Heart Rate, RR in the flag-gated field of `0x2A37`), `0x180F` (Battery), `0x180A` (Device Information). These are level L0.
- **One consumer service** with a feature characteristic notified at 1 Hz (27 bytes, a version, flags, a `sequence`, a per-field "not available" sentinel), a status characteristic (40 bytes), a stream-metadata characteristic and a control point. The firmware fills heart rate, the PPG quality index, the motion-artifact probability and the stress class; the RR, RMSSD and SDNN are "not available" until its RR feature, off by default, is switched on after the bench run. An ATT MTU of at least 30 (43 for the status, 247 for raw frames) must be negotiated.
- **A research service** with raw ECG, PPG, IMU and power streams. Averyn subscribes to it only under the `raw_signals` consent, only while an activity is recording or the live-signals screen is open ([ADR-0030](../adr/0030-synapse-contract-v2-1-and-raw-signals.md), level L1R).
- **FIT developer fields**, flat scalars. The stress enum is `0 = baseline, 1 = stress, 2 = artifact, 3 = unknown`.

### Pairing experience (L0 and L1)

The band is found by the generic strap scan, with the name it advertises, and works as a strap with no setup (L0). Only when the band offers the feature service does the app offer the extra signals, in a separate step that explains in wellness words what is read and asks for the consents it needs one by one (`signal_quality`; `stress_monitoring` for the stress class; `rr_recording` and `hrv_analysis` for the intervals and the band's own HRV; `raw_signals` only for the live and recorded raw signals); declining leaves the band working as a strap. Data produced by the band is labelled "via Synapse" wherever it is shown.

## 2. Levels

See [ADR-0026](../adr/0026-averyn-synapse-link.md) for the table and the rules of L1 (sentinels, loss accounting, timestamps, consent scopes `signal_quality` and `stress_monitoring`, the sidecar, provenance, device binding).

## 3. Data ownership and storage

Averyn stores the device record, the session, the raw file and the consent grant ([ADR-0010](../adr/0010-ecosystem-boundary.md)). Data from a Synapse device enters as **imported data**:

- `source: "synapse-device"` (live frame) or `"synapse-worker"` (a worker result, after launch).
- `algorithm_version`: the producer's own string, passed through verbatim and never coerced into an Averyn `algorithm_version`: Averyn did not compute it and cannot reproduce it deterministically, so it is not a `shared/metrics` type ([ADR-0014](../adr/0014-sensor-integration-contract.md)).
- Displayed with visible provenance ("via Synapse"), never blended silently into Averyn's own charts.

A Synapse inference worker never has its own user database: it receives a job (job id, a reference to a file Averyn stored, a computation type and version, no user identifier) and returns a result keyed to that job id. That is level L3, after launch.

## 4. Auth

No shared service-account token that can query any user's data ([ADR-0011](../adr/0011-identity-oidc.md)). For L3, Averyn mints a short-lived, job-scoped credential per dispatch, and a result is accepted only against that job id. Device provisioning, when it exists, uses a CSR flow: the device generates its key pair and a CSR; a private key is never generated elsewhere and sent to it.

## 5. Consent

Per [ADR-0013](../adr/0013-health-data-special-category.md) and [ADR-0021](../adr/0021-consent-health-data.md), each scope is a separate, revocable grant, checked by the native adapter before it subscribes, and again while it records. Scopes for the Synapse layer: `signal_quality`, `stress_monitoring` at launch; `hrv_analysis`, `sleep_staging`, `raw_data_export`, `research_sharing` are reserved for later levels.

## 6. Canonical GPS source

Per [ADR-0014](../adr/0014-sensor-integration-contract.md): the phone's location stream is canonical. If a device has its own GPS, its track only fills gaps the phone missed; activities are never silently merged from two tracks.

## Open questions

- Whether the firmware will send the real RR in `0x2A37` and fill RMSSD/SDNN (a request to the device repository, tracked in ADR-0026). Until then L1 shows signal quality, motion artifact and the stress class only.
- Whether the sleep-stage field is ever populated without EEG input, and what accuracy claim is honest to show: a product and legal question, not a technical one.
- The worker job/result schema (queue technology, payload): designed when L3 starts.

## 7. What is in place on the server and in the browser (2026-11-07)

- **Server** (`backend`, `synapse` package): `PUT /v1/activities/{id}/synapse/{features|raw}` stores a sidecar as received (its own consent, `410` after a revocation, `507` over the quota); `GET .../synapse` returns the summary (the derived values as parallel arrays with nulls and gaps, and the per-stream account of what the link lost); `GET .../synapse/raw/{stream}?from&to&maxPoints` returns the min/max buckets of a window, per run without a hole, in the contract's display unit. Revoking a consent really deletes: the whole sidecar for `signal_quality` and `raw_signals`, and only the covered fields of the stored frames for `stress_monitoring`, `rr_recording` and `hrv_analysis` (rewritten as "not available"). The pyramid of a recording is built when it is first read and kept in memory (see [`metrics/synapse-series.md`](../metrics/synapse-series.md)).
- **Web**: the activity page shows the derived values and the raw signals, labelled "via Synapse", with zoom and pan, gaps as breaks and as table rows, and a table for every chart ([TDD-0017](../design/TDD-0017-synapse-signal-views.md)). The account page grants and revokes the five scopes one by one.
- **Not done**: the phone side. Nothing yet writes the sidecars on a phone (the Android and iOS adapters, the on-device store and the upload), there is no live-signals screen and no mobile history view. Until that exists the server and the page can only be fed the device repository's synthetic sessions. No band, no phone and no browser has run any of this.
